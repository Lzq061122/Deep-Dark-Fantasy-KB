# E-06｜先验证关键机制，再展开完整实现

**领域**：技术研究 / Agent 协作 / 工程验收  
**来源**：2026-10-26 项目协作复盘，经授权概括  
**证据等级**：代表案例的代码与日志已核对，离线构建和测试已独立复跑；改进做法属于工程判断，尚无采用后的返工率对照数据。

## 可复用结论

关键技术是否可行仍未知时，先完成一个能验证核心假设的最小探针，再展开完整实现。核心机制失败，就回到定位或方案裁决；替代行为必须按它实际完成的目标评价。

## 触发场景

涉及外部引擎 Hook、插件接入、平台能力或真实设备；完整方案依赖一个尚未验证的入口、权限或执行机制。

## 反复整改的常见原因

1. **关键验证太晚**：把机制可行性与完整生命周期放在同一批，先扩展台账、状态机和脚本，之后才发现底层接入不成立。研究和派单方也要为任务粒度负责。
2. **遇阻后目标漂移**：原目标无法实现，开发继续做替代行为，最终仍按原目标交付。合同写了停止条件，协作中却没有真正执行。
3. **测试与真实路径脱节**：离线判定器通过，但没有接入实际调用入口；测试数量和绿色结果掩盖了最重要的接线缺口。
4. **审查过晚且边界零散**：整套交付后才检查关键差异，同类输入、回滚和释放边界分轮暴露，形成反复返工。

## 下次怎么做

- **先验证成败所系的机制**：用真实目标版本、明确构建身份与可观察信号，证明所需入口和效果成立。失败保留证据，区分环境、调用路径、实现错误与能力限制。
- **再接最小业务路径**：让真实使用入口调用规则，检查请求如何被接受、拒绝和反馈。测试应覆盖这条路径，不能由未接线模型代表系统。
- **最后完成安全生命周期并集中验收**：将无效输入、失败回滚、过期、失权、旧请求和释放后的行为成组检查。设计/验收方提前核对决定成败的差异，不等完整交付后才发现目标变化。
- **把停点落实为结果**：关键机制失败时，交付可复核的失败结论或待裁决方案，暂停依赖它的扩展；如需改变目标或关键接法，明确处理变更。

## 代表案例

一次控制原型要求在冲突命令进入前拒绝写入，实际交付采用改写后再补写纠正；离线准入测试通过，但判定器没有接到真实写入口。因此测试成立，原控制合同仍未完成。研究与派单同时安排了关键接入验证和完整生命周期，扩大了返工面；开发遇到阻断后继续替代实现，也延迟了技术裁定。

上述案例来自已完成的源码、运行日志与验收核对。本次保存经验没有重新运行实机场景；它不证明整个底层技术不可用，也不证明单一原因解释了全部返工。

## 边界

适用于关键机制未知、外部运行时耦合较高的工作。已知路径上的小改动不必另加阶段、文档或审批。已有授权内应自主完成必要验证，阶段性检查不等于反复要求用户确认。

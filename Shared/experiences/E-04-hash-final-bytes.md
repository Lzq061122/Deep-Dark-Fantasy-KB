# E-04｜校验文件哈希必须对应最终字节

**领域**：文件 I/O / SHA-256 / Windows 换行转换 / 测试设计  
**来源项目**：CultureLens · Ade  
**核查状态**：当前公开实现与测试断言已核对；历史数值未独立复算。

## 可复用结论

如果 API 返回的是“导出文件的 SHA-256”，哈希必须对应最终文件的**实际字节**，而不是尚未经过写入转换的内存字符串。文本编码、BOM 或 LF/CRLF 转换都可能导致两者不同。

## 触发场景

- 导出、备份、签名、下载、内容寻址或文件一致性核查。
- 在 Windows 和其他系统之间交换文本产物。
- 业务测试通过，而外部工具对同一文件算出的哈希不同。

## 操作原则

- 明确业务契约要求字节一致还是语义一致。
- 使计算哈希所用的字节与写入的字节一致，必要时从落盘文件按二进制读回。
- 测试字节级契约时使用 `read_bytes()` 一类的原始字节读取，而不是会归一化换行的文本读取。
- 对重要文件用独立实现或外部工具交叉核对。

## 代表案例

CultureLens 的验收记录指出，旧版导出对内存字符串求哈希，而 Windows 文本写入发生换行转换，致使返回值与文件字节不一致。后续代码改为对同一份 UTF-8 字节写入并计算 SHA-256，测试对落盘字节读回校验。

## 边界

当契约仅要求解析后的字幕段、时码和文本在语义上相等，不应平白增加跨平台原始字节一致的要求。历史报告中列举的具体哈希数值未在本次复算。

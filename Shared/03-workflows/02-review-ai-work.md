# AI 说“完成了”，我该怎么验收？

> 阅读时间：约 8 分钟 · 从普通聊天任务到编程 Agent 都适用

很多初学者会把 AI 的最终回复当成任务完成的证明。但一个任务的结果可能需要检查文件、运行程序、人工试用或阅读原始资料才能确认。

## 1. 先明确“完成”是什么意思

同样是“帮我做一份表格”，可能有三种不同结果：

- **提出思路**：AI 解释应该有哪些列，但没有创建文件。
- **生成内容**：AI 输出可以复制的表格。
- **交付可用文件**：有真实文件，格式正确，数据经核查，能打开使用。

在委托前说清楚你想要哪一种，验收会容易很多。

## 2. 把结果分成五个检查层次

| 层次 | 要问的问题 | 例子 |
| --- | --- | --- |
| **交付存在** | 真有这个结果吗？ | 文件能下载、页面能打开 |
| **形式正确** | 文件和结构符合要求吗？ | 字段、格式、目录正确 |
| **行为正确** | 能完成核心操作吗？ | 点击保存后内容真的保存 |
| **内容可靠** | 事实、数据和逻辑正确吗？ | 统计口径一致，引用可回查 |
| **边界可接受** | 异常情况、安全与恢复处理了吗？ | 输入错误、保存失败、回滚方式 |

简单任务不必测试所有层次；影响越大、越难撤销，就越需要完整验收。

## 3. 举个例子：AI 帮你做一个网页

假设你的需求是：

> 给我做一个上传文件的网页，用户可以选文件并看到文件名。不要实际上传到服务器。

一个合适的验收过程：

1. **交付存在**：页面文件确实创建；运行后浏览器能够打开。
2. **形式正确**：页面具有文件选择区和显示文件名的区域。
3. **行为正确**：选择文件后，名称正确更新；取消选择时表现合理。
4. **范围正确**：没有擅自加入服务器上传，尤其不能在用户不知情时发送文件。
5. **异常处理**：没有选择文件时也不会报错。

你可以让 Agent 报告它运行了哪些测试，但仍要尽量亲手查看一次效果。

## 4. 编程任务多看三类证据

- **Git diff**：实际更改了哪些文件、删掉了什么？
- **测试输出**：什么测试跑过，退出码与失败情况怎样？
- **运行演示**：真正启动了功能，还是仅仅写出了代码？

如果你刚开始学 Git，在项目目录中可以先用：

```bash
git status
git diff
git log --oneline -5
```

注意：`git diff` 默认主要展示工作区中尚未暂存的变更；如果 Agent 已经提交代码，可以用 `git show <提交SHA>` 或比较两个提交。**不要因为 `git diff` 没输出就推断 Agent 没改过代码。**

## 5. 可以复制给 Agent 的验收要求

```text
请按我原始需求逐条核对交付物。

每条写清：
1. 要求是什么；
2. 具体在哪里实现；
3. 有什么可检查的证据；
4. 是否已经实际测试；
5. 哪些部分未实现或尚未确认。

不要把“计划测试”写成“已测试”。
如果你没有权限执行某项操作，请如实说明。
```

## 6. 什么叫“通过”？

**通过 = 你定义的验收条件，有足够的实际证据支持。**

有时只完成了部分要求，也可以交付“阶段成果”；但应写清剩下哪些工作。大型项目特别需要区分“代码已写”“单元测试通过”“集成验证通过”“真实用户可用”。

# Agent 入门：AI 为什么能读文件、改代码、运行程序？

**建议阅读顺序**：先看[关键概念](../01-basics/01-key-concepts.md)，再看这篇。

## 先理解一件事：给 AI 一个目标，不等于给它一切权限

假设你说：“帮我整理电脑里重复的课程资料。”

普通聊天产品可能只能告诉你整理方法。有电脑文件访问权限的 Agent，则可能列出文件、识别重复项、生成整理建议，甚至执行移动操作。

后者能力更强，风险也更高。**文件移动、删除、覆盖和上传应当有明确的权限与确认环节。**

## 1. 一次 Agent 任务一般是怎么跑的？

```text
用户：这个项目启动失败，帮我找到原因
             │
             ▼
      读取项目文件和报错
             │
             ▼
       判断可能的原因
             │
             ▼
       运行检查或小测试
             │
             ▼
   ┌──结果正确？──否──┐
   │                  │
   是              继续定位
   │                  │
   ▼                  └──回到检查
总结修改、测试和未解决项
```

这是一个**简化的典型流程**，不是说每个 Agent 都按同一套算法运行。它也可能在任何一步做错判断。

## 2. “它能不能执行”取决于三个条件

- **工具是否存在**：有没有读取文件、执行命令、搜索的接口？
- **权限是否允许**：能访问哪些路径、网络和账户？
- **上下文是否足够**：它知道项目目标、已有规则和当前状态吗？

同一个模型在两个软件中的表现不同，原因可能就出在这些地方。

## 3. 什么任务适合第一次交给 Agent？

建议先从**可恢复的小项目**开始，比如：
- 修改一个 README，让内容更易读；
- 为一个小函数补单元测试；
- 搜索代码仓库中未使用的变量并生成报告（先不自动删除）。

不建议首次就让它删除大量文件、操作真实财务数据、提交生产环境变更或拥有全盘读写权限。

## 4. 一个最小安全流程

1. **先备份或提交当前版本**：保证能回退。
2. **只授权需要的目录**：尽量不给全盘权限。
3. **先让它看，再让它改**：特别是删除、重构、迁移任务。
4. **检查修改差异（diff）**：看它到底增删了什么。
5. **运行测试并复核结果**：不要只接受“我测试通过了”的文字。
6. **最后再合并或发布**：部署、公开或发送重要内容前需确认。

对于 Git 项目，可以先学三个命令：

```bash
git status
git diff
git log --oneline -5
```

分别用来查看工作区状态、尚未提交的修改，以及最近五条提交记录。**执行这些命令前要确认自己确实在目标项目目录中。**

## 5. 为什么不建议两个 Agent 直接改同一个文件夹？

想象两个人在没有沟通的情况下修改同一篇文档。A 刚修改第一段，B 依据旧版本改了全文，最终谁的内容留下来就成了问题。

编程 Agent 同时使用同一个 Git 工作目录，也可能产生类似的相互干扰。

更稳妥的方法：
- 每个 Agent 使用单独的分支，必要时搭配独立 worktree；
- 分清各自负责的文件/模块；
- 完成后逐个审查修改，再合并；
- 冲突时由人决定保留什么。

## 6. Agent 做完时，应该怎么汇报？

一份好汇报至少回答：

```text
目标是否达成：
改动了哪些文件：
实际执行了哪些命令：
测试结果和证据：
已知限制：
如何撤销本次修改：
```

如果它没执行测试，就应当明确写“未执行”，不能含糊地声称“没有问题”。

**一句话总结**：使用 Agent 的核心技能，除了提出目标，还包括给对权限、观察过程、保留回退手段与验收最终结果。

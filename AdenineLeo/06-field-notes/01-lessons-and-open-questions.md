# 实战笔记：已经踩过的坑，以及还没验证的猜想

> 更新：2026-10-26
>
> 这是根据过去的使用讨论和已有项目记录整理的**回顾性初稿**，并不是完整的事故日志。为避免把回忆写成事实，下面区分「已观察」「经验判断」「待核实」。

为什么保留不完整记录？因为几个月后“我好像遇到过类似问题”往往只剩这句话；哪怕只有一个错误现象，也能给未来排查留下线索。

## 案例 1：两个 AI 分别修改同一个前端，我不知道最后留下了谁的代码

**场景（已观察）**

在一个视频字幕与文化审核项目 CultureLens 中，曾经在不同设备上安排两次前端修改：一边的修改尚未全部结束，另一边又根据相近需求开始了重构。

**当时遇到的问题（已观察）**

难以确认最终仓库保留的是哪一次修改，以及先前完成的功能有没有丢失。

**可能的风险（经验判断）**

如果两个工作流程建立在不同的代码状态上，后提交的修改可能遗漏先前的工作；如果同时操作同一个工作区，还可能出现文件覆盖。**但是是否真的发生了覆盖，不能仅凭“最终看起来不一样”来判断。**

**建议这样排查**

1. 先看 `git log --oneline --decorate -15`，找出两次工作对应的提交。
2. 用 `git show --stat <提交SHA>` 看各自改了什么文件。
3. 用 `git diff <旧提交> <新提交>` 对照具体变化。
4. 核实关键 UI、功能和测试是否还存在。
5. 下次先为不同 Agent 分配独立分支或 worktree。

**尚未核实**：两次修改的具体提交范围、是否发生功能回退、最终如何合并。今后补上 Git 证据后再写结论。

## 案例 2：想让最强模型“一次性做完”，但产出不一定有效

**场景（已观察）**

在复杂的游戏 AI Mod 研究工作中，曾尝试使用更高推理能力的模型参与设计，希望它提前发现问题并给出更成熟的方案。

**感受与局限（已观察的主观评价）**

有的研究轮次主要是推翻、延伸已有设计，未达到“产生实质新进展”的预期。

**学到什么（经验判断）**

与其给一个巨大而模糊的目标，不如明确它必须交付的产物：可执行算法、输入输出定义、关键假设、反例、验证方案，以及还有哪些未知问题。

**重要区分**：这无法证明某个模型“没能力”。任务定义、可用证据、上下文和验收标准都会影响结果。

## 案例 3：Agent 会读代码，不代表能自动继承另一个 Agent 的上下文

**场景（过往项目技术记录）**

在一套 DeepSeek Harness / Codex 子 Agent 的历史方案中，项目记录指出：某条子 Agent 调用路径下，新启动的 Codex 子进程只继承工作目录，**不会自动继承父 Agent 的完整对话上下文**。

**容易产生的误会**

父 Agent 已经讨论过的产品要求、架构边界和当前决策，子 Agent 并不一定知道。

**当时形成的应对方案**

将任务写成自包含的派单：说明目标、相关文件、不可修改的约束和验收方式。让 Agent 从仓库的状态文档和源代码读取事实，再用 diff、测试和报告验收。

**适用范围注意**：这是**特定历史实现路径**的记录，不能推断所有 Codex、所有 Harness 或当前版本都如此。具体行为需要按所用版本复验。

## 案例 4：“兼容某种 API”也可能无法正常运行整条 Agent 工作流

**场景（过往项目技术记录）**

在尝试连接不同模型服务与编程 Agent 时，已有技术笔记把部分非官方桥接方案归为实验性基础设施，并记录过运行一致性未达标、某些启动或执行路径未闭环等风险。

**为什么会这样（技术解释）**

一个接入点即使支持基础对话接口，也不一定完整支持工具调用、流式传输、会话延续、压缩上下文或进程退出等 Agent 需要的行为。

**以后如何验证**

- 先确认服务可以正常访问；
- 用一个只读的小任务检查工具调用；
- 检查流式返回、错误处理和退出行为；
- 记录测试版本和结果；
- 保留一个已知可工作的回退方案。

**尚未核实**：目前所有相关连接方案在最新版本的兼容性。本条记录仅用于说明“基础调用成功不等于工程闭环成功”。

## 如何把模糊回忆变成可靠经验？

以后发生问题时，不用写长文，只留下这些：

```text
日期/工具/版本：
我原本想做什么：
实际看到了什么：
有没有报错、截图或日志：
我试过哪些办法：
现在解决了吗：
```

连“还没解决、原因不明”也值得记。可以直接复制 [两分钟经验记录模板](../templates/experience-note.md)。
